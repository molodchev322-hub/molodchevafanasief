# Исправление цепочки E-17 для AR-210

## Причина

В исходном `artifacts/graph.json` присутствовала связь `ErrorCode:E-17 -> INDICATES -> Component:пусковое реле` и связь новой детали с поставщиком, но отсутствовали узлы/рёбра из руководства для `Model:AR-210` и `Part:P-1042`. Из-за этого локальный поиск не мог соединить опорные узлы `E-17` и `AR-210` путём длиной до трёх рёбер и завершался отказом.

## Исправление

`assistant.graphrag.extraction` теперь дополняет ответ модели фактами из однозначных текстовых шаблонов. Сам промпт также ужесточён: модель извлекает только прямо подтверждённые текущим чанком связи, не дублирует элементы и пропускает неоднозначные отношения вместо догадки. Это снижает риск раздувания ответа и ложных связей.


- заголовок руководства связывает чанк с моделью;
- строки раздела «Состав узлов» дают `Model -> HAS_PART -> Part`, `Part -> IS_A -> Component` и `Part -> SUPPLIED_BY -> Supplier`;
- строки раздела «Коды ошибок» дают `ErrorCode -> INDICATES -> Component`;
- сервисный бюллетень даёт `Part -> REPLACED_BY -> Part` и связь новой детали с поставщиком;
- регламент даёт `ErrorCode -> FIXED_BY -> Procedure`.

Детерминированные факты добавляются только при точном совпадении кода/названия с текстом чанка и проходят ту же проверку схемы, что и ответ модели. Если для одной пары «субъект + тип связи» документ прямо задаёт объект, противоречащий ответ модели объект отбрасывается.

## Эталонная цепочка

```text
ErrorCode:E-17 -INDICATES-> Component:пусковое реле
Model:AR-210 -HAS_PART-> Part:P-1042
Part:P-1042 -IS_A-> Component:пусковое реле
Part:P-1042 -REPLACED_BY-> Part:P-1042B
Part:P-1042B -SUPPLIED_BY-> Supplier:ХолодКомплект
```

`local_search` находит путь между `E-17` и `AR-210`, добавляет цепочку замен и передаёт модели факты с источниками. ERP остаётся отдельным этапом агента.

## Совместимость модели и вызова инструментов

Проверка старого архива выявила отдельный источник отказа агента: корневой `Modelfile` задавал упрощённый шаблон, который выводил `.Messages` только как `role/content` и не сериализовал `tool_calls` и ответы инструментов в формате Qwen3. Такой шаблон мог приводить к тому, что модель печатала вызов инструмента как обычный текст, а `LLMClient` не получал структурированное поле `message.tool_calls`. Старый `Modelfile` удалён. Проект должен запускаться на модели `qwen3:4b-instruct-2507-q4_K_M` из `.env.example` с её штатным шаблоном Ollama. Это согласует конфигурацию запуска и метаданные новых прогонов.

Официальное описание Qwen3 указывает на отдельную структуру `<tool_call>` для вызовов и `<tool_response>` для результатов; поэтому шаблон с одними `role/content` не подходит для агентского цикла. См. [Qwen3: Tool Calling](https://github.com/QwenLM/Qwen3/blob/main/docs/source/getting_started/concepts.md#tool-calling).
